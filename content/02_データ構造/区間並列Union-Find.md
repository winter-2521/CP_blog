## 何ができるアルゴリズムか？

「$i = 0, \ldots, k-1$ について $a+i$ と $b+i$ を併合する」という **区間同士を並行に併合する** 操作を、全体で $O((n \log n + q)\,\alpha(n))$ で処理する。素朴にやると 1 回 $O(k)$ で全体 $O(nq)$。

>[!問題] Range Parallel Unionfind (Library Checker)
>$N$ 頂点 0 辺のグラフと重み $x_i$ がある。`k a b`：各 $i < k$ について辺 $(a+i, b+i)$ を追加。各クエリ後に $\sum_{i<j, \text{同じ成分}} x_i x_j$ を出力せよ。$N, Q \le 2 \times 10^5$

## 計算量

- オンライン版：全体 $O((n \log n + q)\,\alpha(n))$、メモリ $O(n \log n)$
- オフライン版（クエリを先読み）：計算量は同じ、メモリ $O(n + q)$ で定数倍が速い

## 具体例で理解する

### 何がしたいのか

「$a + i$ と $b + i$ をつなぐ（$i = 0, \ldots, k - 1$）」は、2 つの区間 $[a, a+k)$ と $[b, b+k)$ を **ずらして重ねた位置同士** をつなぐ操作。素朴に $k$ 回 unite すると、毎回 $k \approx n$ のとき全体 $O(nq)$ で遅い。

### 長さ 2 冪の区間をまとめて 1 要素として扱う

段 $j$ の Union-Find では、要素 $i$ が「長さ $2^j$ の区間 $[i, i + 2^j)$」を表す。段 $j$ で「$x$ と $y$ をつなぐ」は「$[x, x+2^j)$ と $[y, y+2^j)$ を位置ごとにつなぐ」の意味。

### 例：$n = 8$

**操作 1：`merge(0, 4, 4)`**（$0\!-\!4, 1\!-\!5, 2\!-\!6, 3\!-\!7$ をつなぐ）

$k = 4 = 2^2$ なので、段 2 で $0$ と $4$ をつなぐ（$[0,4)$ と $[4,8)$）。初めてつながったので下の段へ伝える：

- 段 1：$0\!-\!4$（$[0,2)$ と $[4,6)$）、$2\!-\!6$（$[2,4)$ と $[6,8)$）。どちらも初めてなので、さらに下へ。
- 段 0：$0\!-\!4$、$1\!-\!5$、$2\!-\!6$、$3\!-\!7$。実際の頂点がつながる。

**操作 2：`merge(1, 5, 3)`**（$1\!-\!5, 2\!-\!6, 3\!-\!7$ をつなぐ）

$k = 3$ なので、長さ 2 の区間 2 つで覆う：先頭 $[1, 3)$ と $[5, 7)$、末尾 $[2, 4)$ と $[6, 8)$。

- 段 1：$1\!-\!5$ をつなぐ。初めてなので段 0 へ：$1\!-\!5$（既に同じ）、$2\!-\!6$（既に同じ）。何も起きない。
- 段 1：$2\!-\!6$ をつなぐ。**段 1 で既に同じ** なので、ここで止める（下に伝えない）。

2 つ目の「段 1 で既に同じ」が肝心で、段 1 で $2$ と $6$ が既に同じということは、$[2,4)$ と $[6,8)$ の位置同士は既に全部つながっている。だから下を見る必要がない。

### なぜ速いのか

下の段に伝えるのは「その段で実際に 2 つのグループが 1 つになったとき」だけ。各段でグループが 1 つになる回数は高々 $n - 1$ 回（グループ数が 1 ずつ減るので）。段は $\log n$ 個なので、伝える回数の合計は $O(n \log n)$。クエリ自体は 1 回あたり 2 つの unite から始まるので $O(q)$。

## 証明・仕組み

### ダブリングで区間を分解

段 $j$ の Union-Find は、長さ $2^j$ の区間 $[i, i + 2^j)$ を要素 $i$ として持つ。段 $j$ で $i$ と $i'$ が同じ集合 ⟺ 「$[i, i+2^j)$ と $[i', i'+2^j)$ が位置ごとに同じ集合」という意味にする。

長さ $k$ の併合は、$2^j \le k < 2^{j+1}$ として **長さ $2^j$ の区間 2 つ**（先頭 $[a, a+2^j)$ と末尾 $[a+k-2^j, a+k)$）の併合に分解できる（Sparse Table と同じ重ね合わせ。重なっても併合なので問題ない）。

### 下の段へ伝える

段 $j$ で $x$ と $y$ を併合したら、段 $j-1$ で「前半同士 $x, y$」と「後半同士 $x + 2^{j-1}, y + 2^{j-1}$」を併合する。段 0 まで降りたら実際の頂点の併合。

**ここで、段 $j$ で既に同じ集合だったら下に伝えなくてよい**。既に同じ集合ということは、その情報（位置ごとに同じ）は以前に下の段に伝えた併合の組み合わせから導かれるので。

### 計算量

各段の Union-Find で実際に併合が起きる（集合の個数が減る）のは高々 $n - 1$ 回。実際に併合が起きたときだけ下の段に 2 つ伝えるので、段 $j-1$ が受け取る仕事は $2 \times (\text{段 } j \text{ の併合回数}) + (\text{クエリから直接})$。全段で $O(n \log n + q)$ 回の Union-Find 操作。

### 成分の値の管理

段 0 で実際に併合が起きるたびに「残った根」「吸収された根」をコールバックで受け取れば、成分ごとの和などを普通の Union-Find と同じように管理できる。上の問題なら、併合のたびに $X \mathrel{+}= s_r s_c$、$s_r \mathrel{+}= s_c$。

### オフライン版：段ごとにまとめて処理

オンライン版は 1 回の併合で全段の配列（$n \log n$ 個の int）をランダムに触るのでキャッシュミスが多い。クエリを先読みできるなら、**上の段から 1 段ずつ**、その段の併合（直接のクエリ + 上の段から来たもの）を時刻順に処理すれば、同時に触る配列は 1 段分だけになる。

時刻順に処理すれば、各段の Union-Find の状態は「その時刻までの併合」と同じなので、どの併合が実際に起きるかもオンライン版と一致する（同じ時刻の中の順序は関係ない）。手元で 0.47 秒 → 0.27 秒。

## 例題・類題

- [Range Parallel Unionfind (Library Checker)](https://judge.yosupo.jp/problem/range_parallel_unionfind)
- **回文の制約**：「$S[l..r]$ は回文」は「$S_{l+i} = S_{r-i}$」なので、文字列 $S$ の後ろに $S$ を反転したもの $T$ をつなげて、$S$ の区間と $T$ の区間を並行に併合すれば扱える。最後に成分の個数から「何通りの文字列があるか」を数える問題など。
- 「区間 $[a, a+k)$ と $[b, b+k)$ が等しい」という制約がたくさん与えられる問題全般。
